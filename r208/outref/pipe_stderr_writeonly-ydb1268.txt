#----------------------------------------------------------------------------------------------------#
# [YDB#1268] The stderr= device of a PIPE is readable even when the OPEN specifies writeonly          #
#----------------------------------------------------------------------------------------------------#

# A PIPE OPENed with both writeonly and stderr="devname" produced a stderr device that could not be
# READ: the first READ got DEVICEWRITEONLY, Cannot read from a write-only device. So there was no way
# to ask for a command stderr without also taking its stdout, the workaround being to drop writeonly,
# which makes YottaDB create a stdout pipe that the application then has to discard.
#
# sr_unix/iopi_open.c builds the stderr device and fixes its direction, setting read_only on it, but
# then opens it with the same deviceparameter list the caller gave the PIPE. sr_unix/iorm_use.c walked
# that list and set write_only on the stderr device too, and sr_unix/iorm_readfl.c refuses a READ from
# a write_only device.
#
# The first assertion of stage 1 is the failing case. Its other two assertions, and stages 2 to 4, all
# pass on a build without the fix: they are here so that a fix which cleared the direction altogether,
# rather than leaving the one iopi_open.c set, does not go unnoticed.
#
# Each stage runs in its own process, so a device left in a bad state by one cannot affect the next.

# Stage 1 : OPEN with writeonly and stderr="perr1"
# Command : $ydb_dist/yottadb -run wonly^ydb1268
#   expect the stderr device to give [to-stderr], a WRITE to it to be refused with DEVICEREADONLY,
#   and a READ from the PIPE device itself to be refused with DEVICEWRITEONLY
PASS : the stderr device of a writeonly PIPE can be READ, and gave [to-stderr]
PASS : a WRITE to that stderr device is still refused (DEVICEREADONLY)
PASS : a READ from the writeonly PIPE device itself is still refused (DEVICEWRITEONLY)

# Stage 2 : OPEN with readonly and stderr="perr2", which worked before the fix
# Command : $ydb_dist/yottadb -run ronly^ydb1268
#   expect the stderr device to give [to-stderr]
PASS : the stderr device of a readonly PIPE can be READ, and gave [to-stderr]

# Stage 3 : OPEN with stderr="perr3" and neither direction, which worked before the fix
# Command : $ydb_dist/yottadb -run plain^ydb1268
#   expect the stderr device to give [to-stderr] and the PIPE device to give [to-stdout]
PASS : the stderr device of a plain PIPE can be READ, and gave [to-stderr]
PASS : the PIPE device itself still gives the command stdout, and gave [to-stdout]

# Stage 4 : CLOSE and re-OPEN reusing both device names in one process
# Command : $ydb_dist/yottadb -run reuse^ydb1268
#   expect both OPENs to read [to-stderr] from the stderr device they name
PASS : first OPEN, writeonly, reads its stderr device, and gave [to-stderr]
PASS : second OPEN, readonly, reusing both device names reads it too, and gave [to-stderr]

# Stage 5 : OPEN with noreadonly and stderr="perr6"
# Command : $ydb_dist/yottadb -run nord^ydb1268
#   expect the stderr device to give [to-stderr] and a WRITE to it to be refused with
#   DEVICEREADONLY. Without the fix, noreadonly clears the read_only that iopi_open.c set, so
#   the WRITE reaches the OS and fails with a bare ENO9 instead.
PASS : the stderr device of a noreadonly PIPE can be READ, and gave [to-stderr]
PASS : a WRITE to that stderr device is still refused (DEVICEREADONLY)

# Done
