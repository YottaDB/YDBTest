#----------------------------------------------------------------------------------------------------#

# ZYENCODE to a global variable stores the JSON string in chunk nodes, with the chunk number as an
# added subscript. Each stage runs stage<N>^ydb1378 in a new process on a separate database (maximum
# key size 64, maximum record size 256), which checks the error that ZYENCODE issues (if any) and what
# ZYENCODE stored, and then checks the database with MUPIP INTEG (dbcheck.csh).

# Stage 1 : ZYENCODE ^gvn=lvn, with a destination key that is too long once the chunk number is added
# (from fuzz testing)
# Command : $gtm_dist/mumps -run stage1^ydb1378
# Before the fix : a Debug build failed an assert in op_gvput.c; a Release build stored the node and
#                  INTEG reported DBGTDBMAX
# With the fix   : expect GVSUBOFLOW, nothing stored, no INTEG error
PASS : GVSUBOFLOW as expected
PASS : $data(^j)=0 (nothing was stored)
PASS : dbcheck.csh found no database integrity errors
