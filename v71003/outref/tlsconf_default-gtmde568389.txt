# Release note (from http://tinco.pair.com/bhaskar/gtm/doc/articles/GTM_V7.1-003_Release_Notes.html#GTM-DE568389)

# The Receiver Server defaults SSL_VERIFY_PEER and SSL_VERIFY_FAIL_IF_NO_PEER_CERT if the ID in the TLS configuration file does not specify a verify-mode. Previously, the Receiver server defaulted to SSL_VERIFY_PEER. Customers desiring prior behavior should set verify-mode in the configuration file to just SSL_VERIFY_PEER. (GTM-DE568389)
# 

# Create a database

# Revise TLS configuration to omit client server certificate and verify-mode specification
# This will cause verify-mode to be implicitly set to 'SSL_VERIFY_PEER|SSL_VERIFY_FAIL_IF_NO_PEER_CERT'.
# Previously, this would be set to only SSL_VERIFY_PEER by default.

# Start source replication instance
==Executing MULTISITE_REPLIC 'STARTSRC INST1 INST2 RP'==
# Start receiver replication instance
==Executing MULTISITE_REPLIC 'STARTRCV INST1 INST2'==

# Wait for TLSHANDSHAKE error from RCVR server, due to missing client server certificate.
# A client server certificate is required when verify-mode includes SSL_VERIFY_PERR|SSL_VERIFY_FAIL_IF_NO_PEER_CERT.
# Previously, no TLSHANDSHAKE error would be issued and the RCVR server would continue to operate,
# since verify-mode would be set to SSL_VERIFY_PEER only, which makes a client server certificate optional and not required,
# thus allowing continued RCVR server operation.
==Executing MULTISITE_REPLIC 'RUN INST1 $gtm_tst/com/wait_for_log.csh -log ##REMOTE_TEST_PATH##/instance2/##FILTERED##RCVR_##TIMESTAMP##.log -message TLSHANDSHAKE -duration 30'==
----------
Error TLSHANDSHAKE seen in ##REMOTE_TEST_PATH##/instance2/##FILTERED##RCVR_##TIMESTAMP##.log as expected:
%YDB-E-TLSHANDSHAKE, Connection to remote side using TLS/SSL protocol failed
----------

==Executing MULTISITE_REPLIC 'STOPRCV INST1 INST2'==
==Executing MULTISITE_REPLIC 'RUN INST1 set msr_dont_chk_stat ; $MUPIP rundown -region "*" -override >>& mupip_rundown.out'==
